# CQRS application interfaces

These interfaces define the application boundary for `FR-DISPATCH-001` and `TR-DISPATCH-ARCH-001`. The [C4 workspace](workspace.dsl) shows the owners and dependencies. The [ViewModel contracts](presentation.md) and [UI command catalog](ui-commands.md) specify how those interfaces bind to desktop intents.

## Requests, handlers, and results

```csharp
public interface ICommand<TResult> { }
public interface IQuery<TResult> { }

public readonly record struct RequestContext(Guid CorrelationId, Guid? OriginInstanceId);
public readonly record struct CommandContext(RequestContext Request, Guid OperationId);

public interface IRequestDispatcher
{
    Task<Outcome<TResult>> SendAsync<TResult>(
        ICommand<TResult> command, CommandContext context, CancellationToken cancellationToken);

    Task<Outcome<TResult>> QueryAsync<TResult>(
        IQuery<TResult> query, RequestContext context, CancellationToken cancellationToken);
}

public interface ICommandHandler<in TCommand, TResult>
    where TCommand : ICommand<TResult>
{
    Task<Outcome<TResult>> HandleAsync(
        TCommand command, CommandContext context, CancellationToken cancellationToken);
}

public interface IQueryHandler<in TQuery, TResult>
    where TQuery : IQuery<TResult>
{
    Task<Outcome<TResult>> HandleAsync(
        TQuery query, RequestContext context, CancellationToken cancellationToken);
}

public sealed record ValidationIssue(string Code, string? Field);

public abstract record Outcome<TResult>
{
    public sealed record Success(TResult Value) : Outcome<TResult>;
    public sealed record Invalid(IReadOnlyList<ValidationIssue> Issues) : Outcome<TResult>;
    public sealed record Conflict(string Code, long? ActualRevision) : Outcome<TResult>;
    public sealed record Cancelled : Outcome<TResult>;
    public sealed record DependencyFailure(string Code, bool Retryable) : Outcome<TResult>;
}
```

- Register exactly one handler per concrete request type and result type. Validate registration at composition time. Configuration and diagnostics can run with the bootstrap registrations before opening the normal stores and services.
- The entry point creates a new correlation ID for each dispatch. Retried commands carry the original operation ID for the same intent. The host binds origin identity to the authenticated instance. Commands replacing durable state carry the relevant expected revision in the command payload.
- Return typed validation, conflict, cancellation, and dependency outcomes. Validation codes remain stable for their callers. A durable commit or accepted job retains its receipt even if the caller cancels after that point. Check the recorded operation or job identity before retrying an uncertain external effect.
- Queries read immutable snapshots within the relevant owner scope. Versioned query results include that owner's revision when needed. The presentation owner and request stamp govern projection into the current ViewModel. Route application-driven presentation updates through the Avalonia scheduler.

## Ownership, mutation, and recovery

Handlers use the typed [LiteDB repository ports and write unit of work](persistence.md). Repositories for one command share the same transaction. CQRS outcomes reach a caller after that transaction commits or rolls back.

- **Desktop bootstrap.** The configuration handler validates the proposed effective paths and restart-bound configuration. It preserves known and unknown JSON keys and opens local state only after path validation and any required creation approval. Repair is available before playback, plugins, and the normal Library start.
- **Desktop state.** The playlist workspace owns draft writes by draft identity. Playback owns active queue writes by session. Settings own preference overrides. The adapter schedules writes per database file and commits changes with their replay record when applicable. Handlers return snapshots or revisions after commit.
- **Local batch control.** `GetLibraryBatchMode` returns the toggle, revision, count, and whether an approved commit or private-copy cleanup is awaiting resolution. `SetLibraryBatchMode` applies only at the observed revision. Turning off a dirty batch returns a resolution conflict. `GetLibraryBatchReview` returns all staged changes in insertion order with the review ID and revision. `CommitLibraryBatch` freezes that exact approval and hands the entire reviewed batch to `IApprovedLibraryBatchPublisher` as one operation. `ResumeLibraryBatchCommit` reloads the frozen approval and original operation ID after an uncertain result or desktop restart. The tag editor, playlist saves, queue auto-save, import copies, organization, and removal use this boundary when composed with the batch handlers.
- **Batch revert.** `RevertLibraryBatch` clears the exact local revision. Unsubmitted changes are discarded locally. A sealed approval requires a durable withdrawal receipt for the exact library, owner, approval operation and reviewed revision before the desktop clears its entries and private copies. The host fences delayed submissions by recording the withdrawal even when the approval has yet to arrive. An uncertain response leaves the local entries available for another revert attempt. If native execution has started or the batch has published, the host returns a conflict and the desktop preserves the seal.
- **Approved batch publication.** The host validates the complete reviewed submission, journals entries in order, and reserves the original operation IDs and maintenance plans. A playlist-only batch applies its approved updates in one peer revision. A batch containing native work verifies its baselines before starting, checkpoints actions in review order, and reserves the affected saved playlists during execution. It publishes the verified catalog updates, tombstones, playlist versions, and peer deliveries in one transaction. A pre-write rejection releases the desktop seal for revert. A running batch keeps its seal through restart and the desktop binds named drafts when the terminal receipt returns. Repeated saves of one draft use a single playlist identity.
- **Approved import copies.** After host admission, the desktop opens the reviewed local copies and transfers only the files without host receipts. Each transfer is scoped to the originating desktop, approval, entry, ordinal, and file ID. The host verifies the declared size and SHA-256 before it records the receipt. After restart the same review reports the confirmed parts, so the desktop sends only the missing files. Approved import bytes stay outside the music tree, peer shares, and direct guided-import storage until batch execution.
- **Guided review within an approved batch.** The host discovers candidates for an import entry after its private files all verify. `GetLibraryBatchImportReviews` returns `LibraryBatchImportReviews` with the ordered file names, offered match comparisons, and recorded decisions. `ChooseLibraryBatchImportAction` specifies the batch version, entry operation and position, displayed review revision, and Keep tags, Use match, or Skip. It returns `LibraryBatchImportChoiceReceipt`, which the originating desktop can retrieve by replaying the same operation. Private provider data stays on the host. The batch stays accepted until every import choice is recorded and its executable inputs verify. Beets applies Keep tags from the verified upload and Use match from a privately prepared copy. After interruption, the host checks the exact choice marker and verifies the album before publication. Skip leaves the catalog untouched. An all-skip batch completes at the current revision, including an empty feed at revision zero.
- **Batched tag and playlist edits.** `GetTrackTags` reads the cached track revision and applies pending patches for the selected track while batch mode is enabled. `EditTrackTags` checks that revision and stores the exact before and after fields. `SavePlaylist` saves the draft's submitted name and ordered entry identities to the review without updating its authoritative backing. Both return a typed `LocalBatch` receipt for the ViewModel. The shared mutation lane serializes the toggle with the decision to stage or submit. Receipts keep replay on the chosen route across restart and prevent a discarded edit from falling through to direct publication.
- **Batched queue auto-save.** `EnqueueTracks` and `EditQueue` use the same mode gate when a queue backed by a saved playlist auto-saves. With batching enabled, one local transaction saves the new playback checkpoint and its staged playlist order. `PlaybackState.Queue` exposes `StagedInBatch` and the local receipt. On commit, the desktop stores the authoritative playlist version on the original queue operation receipt. Playback adopts that version before the next queue edit, including after restart, and reports `Saved` for the matching queue revision. A newer playback-only order stays local. Reverting discards the playlist save and clears its staged status when the queue refreshes. Background replay pauses while batch mode is on. Earlier direct operations can resume with their original IDs after batching is disabled.
- **Host state.** Host commands validate authorization and expected revision against the host's state. For external library commands, persist accepted intent and stable job identity before calling beets. Reconcile actual catalog and file effects, then commit the new revision and delivery records together. The submission's success value is a job receipt. Query job status independently of the submitting request.
- **Guided import intake.** `SelectImportSources` returns an opaque local selection. `UploadImportSources` binds it to the current registered library and operation. The host pins the selected file order, names, byte lengths and hashes to the registered desktop and upload ID. `StartImport` checks all private copies before committing the accepted job. If its reply is lost, the desktop reuses the completed upload and the same operation ID. The host retains a single job across retries and restart. `GetLibraryJob` reads the originating desktop's job without publishing any catalog revision.
- **Batched imports.** With batch mode enabled, `UploadImportSources` verifies private copies on the originating desktop and returns a local stage receipt. The review lists the files in selection order with size and digest. The copy claim exists before the first file is written, so recovery can release unadmitted or retired copies after interruption. The local stage retains its original reviewed bytes and receipt across restart, even if the source file changes. Revert releases the copies while preserving the originals. New start, choice, and retry requests on existing hosted jobs are deferred while the local batch is enabled. Existing hosted job status remains readable.
- **Guided import review.** `GetLibraryJob` returns the ordered album source names and offered matches while the job awaits approval. `ChooseImportAction` submits the chosen match, Keep tags, or Skip against that review item and revision. The host keeps the beets provider key private and commits one decision with its operation receipt. The desktop reuses that identity after a lost reply. Skip ends the job without a catalog revision. Match and Keep tags record intent for the beets worker.
- **Match preview and application.** When matching is enabled, candidate search sends the original album and album-artist tags to MusicBrainz. Beets previews each release in a disposable catalog without changing staged files. The host and ViewModel both restrict approval to complete matches. The approved release and exact per-source track IDs stay in the job. The worker prepares tagged copies in private, reads their embedded tags and verifies their encoded audio streams against the originals. It records the prepared files and hashes before importing those exact copies into the live catalog. A changed proposal fails before the live attempt begins.
- **Guided import publication.** The publisher accepts an observation scoped to the approved job, upload and choice. Every staged input ordinal must have a reconciled native track with a unique path and beets item ID. One host transaction updates the catalog, revision feed, peer delivery rows and job status. Replaying an identical observation returns the original publication revision. A partial or conflicting observation leaves the catalog revision unchanged.
- **Guided import recovery.** Before invoking live beets, the worker records `NativeAttempted` for the approved choice. Keep tags compares native output with the original staged hashes. Use match compares native output with the prepared hashes and approved release identities. `RetryLibraryJob` resumes the same failed job at its displayed revision. Once live beets may have started, the worker only reconciles its effects. A complete readback can publish after restart. Incomplete effects stay recoverable without repeating the native write.
- **Track tag edits.** Registered desktops read and submit tags at `GET` and `POST /api/v1/libraries/{libraryId}/tracks/{trackId}/tags`. `GetTrackTags` uses the selected track's revision, so unrelated feed advances leave an open draft valid. `EditTrackTags` accepts `title`, `artist`, `albumartist`, `album`, `year`, `disc`, `track`, and `genre`. A null value clears a field. The host commits the revision-pinned patch, baseline, and operation receipt together. The serial beets worker verifies the native item ID, path and prior values before recording its write checkpoint. It applies track-level tags in place. Once a write may have started, restart or retry checks the beets catalog and embedded tags before resolving the same job. Only verified results advance the catalog and record peer deliveries. `GetLibraryJob` returns the current job to the submitting desktop.
- **Maintenance previews and confirmation.** `GetOrganizePlan` and `GetRemovalPlan` call the authenticated host preview endpoint with the ordered track selection and catalog revision. A beets dry run supplies the exact organization destinations. Catalog-only removal has no audio paths. Audio removal verifies the selected paths and requires its explicit approval. `OrganizeTracks` and `RemoveTracks` submit the exact plan ID, revision, and mode when batch mode is off. The host persists the scoped preview and returns the same accepted job when the desktop retries the same operation. With batch mode on, the desktop retains the approved preview in its ordered local review and returns a local stage receipt, even if it disconnects after loading the preview. Revert discards the staged effects. The host catalog, peer feed, and media stay at their previous state during preview, local staging, and job admission.
- **Catalog-only execution.** The host rechecks the pinned selection and records that the native operation may start. It removes matching beets entries while retaining their audio files. After interruption, it reads every approved item again and applies the remaining removals. A changed native identity or path requires a fresh preview. After verifying the full selection is gone, the host removes its track rows, appends one revision with a tombstone for each track, and queues active peer notifications in the same transaction as the job update. `GetLibraryJob` exposes that revision and `RetryLibraryJob` reopens the same plan after a retryable failure. The approved native batch worker uses the same removal adapter and defers its tombstones until the whole review publishes.
- **Explicit audio deletion.** An audio-removal preview privately pins the selected files' lengths and SHA-256. Direct and batch confirmation both require explicit audio approval at that plan revision. The worker checks catalog identities, paths, and fingerprints before starting, then removes each native item before deleting the verified file. It rechecks that no native record refers to that path. In a batch, earlier verified tag edits may update the expected bytes at a reviewed path. Earlier organization may update the native catalog path. The file deletion stays at the original reviewed path, so a new organized copy is retained. An older preview without fingerprints or a replacement found before execution requires a fresh preview. Recovery resumes only effects whose catalog and file state reconcile, and the worker holds publication while any file conflicts with the approved intent.
- **Organization execution.** Organization rechecks source identities and exact reviewed destinations, then persists each source length and SHA-256 before writing. It copies to the approved paths, verifies the files, retains the originals, and repoints the corresponding beets records. A destination occupied before execution fails the plan. Recovery verifies copies and native paths before repeating any work. In a batch, later tag edits and catalog-only removals use the organized path. The worker rechecks retained originals and the final organized file bytes, including fingerprints recorded after later tag edits. The host publishes one final track row or tombstone per track with the rest of the batch.
- **Working catalog.** `BrowseCatalog` applies staged organization and removal for the configured originating desktop. Removed tracks disappear from track and search results and from artist, album, and playlist membership. A staged move exposes its destination in the track row. Playback still opens the committed path until publication. Page cursors bind both the authoritative catalog revision and local batch revision. Revert restores the committed paths and membership on the next read, including after restart.
- **Incremental catalog replication.** `GetReplicationStatus` reads the desktop's durable cursor. `ResumeReplication` in incremental mode captures the host's upper revision on page one and reuses it until the window ends. Each complete page applies catalog, saved playlist, favorite, play, and eligible default changes together with its contiguous cursor in LiteDB. The desktop acknowledges after commit. An interrupted acknowledgement resumes forward from the durable cursor. Notifications and acknowledgements are scoped per registered recipient. An expired cursor records that a snapshot is required.
- **Desktop registration.** `GetRegisteredInstances` reads the current host registry revision. A provisioned credential awaiting enrollment receives an empty roster with that revision. `RegisterInstance` uses an opaque selection in the local OS credential provider and enforces the configured HTTPS endpoint. `RevokeInstance` uses the approved overlay's target and revision. The host limits this command to active Operators. Both writes preserve exact authorized replays by operation ID.
- **Registered desktop activity.** After HTTPS credentials and library scope verify, the host records the active desktop's Last seen value from its UTC clock. Writes are coalesced to one per minute per desktop and exclude revoked and unregistered identities. Observations leave the authorization revision unchanged. The desktop retains the latest observed timestamp when an older receipt arrives.
- **Native beets setup.** `GetHostLibraryState` reports the provisioned native catalog. `GetHostLibraryConfiguration` supplies the separate catalog and YAML locations and the effective host settings. An active Operator explicitly submits those selected values and the observed revision to `InitializeHostLibrary`. The host stages an empty native catalog and generated YAML privately, records both hashes, and verifies the file copies before recording the result. A retry uses the same origin and operation ID. An occupied destination with different bytes requires repair.
- **Native beets configuration.** `SaveHostLibraryConfiguration` uses the displayed revision and the authenticated Operator identity. The private host endpoint preserves the provisioned location identity, validates the supported import behavior, and probes the selected host-approved plugin names. It commits the typed profile and exact operation receipt together. Later native commands load the new revision from LiteDB and generate private YAML without replacing the provisioned base file.
- **Automatic replica refresh.** `RefreshReplication(libraryId, instanceId)` uses the same serialized incremental route and the registered desktop's durable cursor. It returns the resulting `ReplicationState`. Each registered workspace starts an independent pull at activation and retries with backoff after failure. An unconfirmed acknowledgement is retried from the already committed cursor. A snapshot-required result leaves snapshot recovery available through `ResumeReplication`.
- **Listening and default records.** `PublishLibraryRecordRequest` carries an authenticated origin, an operation ID and one `LibraryRecordIntent`. The host checks the expected record revision for a favorite or shared default and preserves the original receipt on retry. Play IDs merge identical history entries and reject changes to an existing play. The versioned defaults registry accepts automatic fade duration, the sync-completion flag, and the Appearance theme. Removing a favorite or clearing a default retains the deletion revision in both the feed and replacement snapshots. Desktop pending operations and local overrides are outside the replaced projection.
- **Offline listener writes.** `SetFavorite` and `RecordPlay` stage their exact operation locally. `GetFavorite` and `GetListeningHistory` expose the pending value alongside confirmed state. When `ResumeReplication` reconnects an outbox-enabled desktop, it replays in original order before capturing the pull window. Success settles a local intent and updates the received record if its revision is current. A subsequent favorite on the same track pins its predecessor's accepted revision before sending. A stale write retains a conflict. `ResolveReplicaConflict` can keep the host value or queue a new favorite intent at the explicitly reviewed host revision. Play identity conflicts can keep the host record.
- **Playback history capture.** The playback handler stages one local play when the backend confirms a new playing occurrence. Pause, seek and continued playback retain that occurrence. Starting the next queue entry captures a new play even when the track ID is repeated. Explicit Stop ends the occurrence. A stored primary occurrence is reused when its queue entry resumes after reopening. The checkpoint and play operation commit in one transaction, and an uncertain receipt is retried with the same play ID and UTC timestamp.
- **Playback lifecycle.** `InitializePlayback` and `SavePlaybackForRestart` take the playback session ID and return `PlaybackState`. Startup resumes only when the local `playback.resumeAfterRestart` flag is on and the checkpoint contains a previously playing entry in a saved playlist. The same queue occurrence starts at the saved position. `GetPlaybackState` restores state without starting audio. An unavailable track leaves the entry and position available and returns a retryable `playback-resume-track-unavailable`. The shutdown command reads the loaded primary deck and stores its latest position and status.
- **Playback checkpoint retry.** If a transport command changes audio before its checkpoint write fails, the live playback session retains its operation ID and intent. A retry with that ID repairs any pending checkpoint and returns the current session state. Later commands can advance playback before the retry arrives. Reusing the original ID with different intent returns `playback-operation-reused`.
- **Mixer and EQ.** `SetMix` accepts normalized master or deck gains and a manual crossfader position from 0 through 1. The blender applies `1 - position` to deck A and `position` to deck B after each deck's gain. `SetEqualizer` applies ten band values from -12 through +12 dB to the mixed output, resets them to flat, or bypasses the filter while retaining the settings. Both commands return the session state after the backend accepts the change. The mixer snapshot reports the independent deck gains and separate crossfader position.
- **Automatic crossfade.** `SetMix(AutoFadeEnabled)` controls the active session. The desktop loop issues `AdvancePlayback` with the session ID. This command reads the outgoing deck clock and the effective fade duration. It prepares the next queue occurrence on the other deck before blending and limits the overlap to remaining audio. Pause freezes the two decks and the blend. Seek or skip cancels the overlap and recomputes from the new position. A manual fader edit takes over the current occurrence. If preparing the incoming track fails, the outgoing deck stays audible and `MasterOutput.FadeErrorCode` reports the failure. After a successful fade the incoming deck and its precise queue occurrence become active.
- **Playback preferences.** Playback settings resolve the local override, last observed shared default, then the built-in value. The restart flag defaults to off and can be edited only locally. Automatic fade duration defaults to zero and accepts an eligible host default. Local writes and clears check the playback category revision before returning the current effective value and its source.
- **Appearance preference.** `GetPreferenceCategory("appearance")` loads the theme. `SetLocalOverride` applies it at the draft's local revision, and `ClearLocalOverride` returns the inherited theme at the accepted revision. `EffectivePreference.SharedDefault` carries the cached shared value even while the local override supplies the effective value.
- **Catalog snapshot recovery.** `ResumeReplication` in snapshot mode captures the recipient's catalog, favorites, history and eligible defaults at one upper revision. Both stores retain the capture identity through restart. The desktop stages each page separately, then replaces only that library's synchronized state and sets the cursor in one transaction. Drafts, pending operations, batch entries and media remain available. Later changes arrive through incremental replication.
- **File publication.** Device export mutations scope work to the selected device, share, and profile version. Compare intended paths against destination availability and the export manifest before publication. After publication, `GetMediaTransfer` reads the verified receiver checkpoint. `ResumeMediaTransfer` makes eligible work due again at the expected revision and can replay its original accepted response. Device export owns staged files and any replay or reconciliation records.
- **Media pairing.** `PairMediaPeer` submits the registered peer, share kind, approved destination and optional Android layout at the expected media directory revision. The host resolves native identities and endpoints from its registration and local configuration, persists the operation fence, and offers the selected sender folder. The response returns the registered peer and share snapshot, and retries with the same operation and intent recover that original result. The receiving peer accepts the share through Syncthing. `GetMediaSyncState` checks that the accepted Android folder still matches the approved scope and advances the directory revision when its observed condition changes.

## Initial request families

The names and fields below specify application intents and results. The feature adapters can exercise these boundaries with headless callers.

| Owner | Queries and result | Commands and result |
| --- | --- | --- |
| Configuration | `GetBootstrapState → BootstrapState`, `GetPreference → EffectivePreference` with its source and revision | `InitializeDesktop` and `SaveBootstrapSettings` take settings and creation approval when required. `SetLocalOverride` and `ClearLocalOverride` return the recomputed preference. |
| Catalog | `BrowseCatalog` takes category, filter, sort and page. `GetTrackAvailability` takes stable track IDs. Results carry catalog revision, stable IDs, metadata, and availability. | Catalog housekeeping and host mutations use their respective writers. |
| Playlist workspace | `GetPlaylistDraft` takes draft ID and returns ordered track IDs and revision. | `CreatePlaylistDraft`, `EditPlaylistDraft`, and `SavePlaylist` return the resulting draft or saved playlist receipt. Edits specify ordered IDs and expected revision. Creation from a queue takes its snapshot. |
| Playback | `GetPlaybackState` takes playback session ID and returns queue, active track, deck state, and capabilities. | `EnqueueTracks`, `Transport`, `Seek`, and `ChangePlaybackStrategy` take the session ID and return current playback state. Playback keeps its session identity through presentation changes. |
| Extensions | `GetPluginState` returns local trust, active worker status, and validated contribution metadata. | `SetPluginTrust` and `SetPluginEnabled` take plugin ID and version, returning the updated local state. A contributed action enters the same dispatcher as an application action. |
| Host library | `GetLibraryJob` takes a job ID and returns its current status, review choices, recovery state, or publication revision. `GetTrackTags` takes a track ID and returns the editable tags and that track's revision. | `StartImport` takes a completed upload ID. `ChooseImportAction` takes the job ID, choice and expected revision. `EditTrackTags` takes the track ID, edited fields and the revision returned by `GetTrackTags`. Each returns a job receipt. |
| PC mirror | `GetMediaSyncState` returns the registered directory, including confirmed PC mirror connections and file progress. The stored observation keeps the last verified count available during pause and host restart. | `SetMirrorPaused` carries the selected PC share and its expected control revision. `RescanMediaShare` rescans that mirror's receiving folder. Both return `MediaSyncState` and preserve the original response for the same authenticated operation. |
| Device export | `GetDeviceLayouts` returns the registered device's player profiles, revisions, path templates, playlist formats and suggested roots. `GetDeviceExportPlan` takes the device ID, the selected profile ID and revision, and an optional plan ID. It returns the saved ordered playlist entries and staged audio for that scope, or an empty plan when the selected profile has no staged entries. | `StageTracksForDevice` and `StagePlaylistForDevice` take the device ID, profile ID and revision, and optional existing plan ID and revision. Direct tracks retain their intent even when a playlist also needs the same audio. `EditDeviceExportPlan` removes selected entry IDs at the expected plan revision and retains audio still needed by another playlist. Staged edits advance the revision and invalidate prior review. `PrepareDeviceExportPreview` returns the reviewed plan revision, ordered file changes, blocking issues and proposed removal paths. `PublishDeviceExport` takes a plan ID, expected plan revision and optional scoped approval, and returns `Published(ExportPublicationReceipt)` or `ConfirmationRequired(OwnedRemovalProposal)`. The HTTPS handlers preserve the originating instance and CQRS operation ID across retries. |

The [UI command catalog](ui-commands.md) specifies how MVVM Toolkit commands dispatch these application requests and project the corresponding typed results. Shell handlers own process-local navigation state. Host and persistence boundaries retain the ownership defined above.

## Verification seams

`DISPATCHAcceptanceTests.Routing_MatchesContract` exercises unique registration, typed validation and cancellation. `DISPATCHAcceptanceTests.Responsive_MatchesContract` holds a host job open while sending independent requests and tests that mutations publish consistently. `DISPATCHAcceptanceTests.Update_MatchesContract` exercises result scope and out-of-order completion when the presentation contracts bind to this dispatcher. Use a recording handler, an immutable query fake, a controllable job adapter and a queued scheduler.
