# Code structure and implementation order

1. Define the [C4 boundaries](workspace.dsl) and [CQRS interfaces](cqrs.md). Establish request types, state ownership, transaction boundaries, result handling, and test seams.
2. Define [ViewModels](presentation.md) and [UI commands](ui-commands.md) against those application contracts. Specify ownership, typed request/result bindings, and projection rules for completion, cancellation, conflicts, and errors.
3. Implement screens last. Bind views to the defined ViewModels and UI commands, then verify each implemented change against the approved Asset Review state and storyboard path.

## .NET solution and planned project boundaries

The solution contains the desktop application and adapter projects, the host application and versioned contracts, and separate unit and integration projects for both. `build.ps1` runs `Compile`, `Test`, `TestGroups`, and `MigrationIntegrationTests` through Nuke. `LibraryHostStartup` composes the HTTPS API, LiteDB store and transfer workers. The standalone host binds one configured HTTPS listener and reads its credentials and certificate from the launching user's OS stores. `DesktopStartup` is the headless lifecycle entry point for configuration, library and playback services. The desktop executable remains planned.

`Desktop` references `Desktop.Application`, `Host.Contracts`, `Plugin.Protocol`, and `CommunityToolkit.Mvvm`. `Host` references `Host.Contracts`. The Desktop composition root binds application interfaces to adapters. `Desktop.Application` keeps its request, result and port types independent of the MVVM Toolkit, Avalonia, LiteDB, process execution, and HTTP payloads. Both protocol projects contain transport-facing records and no runtime state. Host job decisions depend on interfaces for storage and external commands. UI bindings, LiteDB documents, and HTTP payloads each stay inside their own boundary. [LiteDB repository contracts and collection ownership](persistence.md)

## Standalone host

Build with `./build.ps1 Compile` and run `dotnet <compiled-host-dll> --config <host-settings.json>` under the account that owns the credentials and TLS certificate. The example uses Linux paths and binds to loopback. Replace its IDs and paths with local values and select the intended private network address for remote access. The certificate thumbprint selects a valid certificate with its private key from the current user's Personal certificate store. Desktops must trust that certificate and use a host name or address covered by it.

```json
{
  "host": {
    "libraryId": "c2320065-563c-4bf9-821f-9e25f6f2a679",
    "databasePath": "/srv/beets-man/private/host.db",
    "musicRoot": "/srv/beets-man/music",
    "privateStageRoot": "/srv/beets-man/private/stage",
    "publicationWorkRoot": "/srv/beets-man/private/work",
    "androidExports": []
  },
  "listener": {
    "address": "127.0.0.1",
    "port": 8443,
    "certificateThumbprint": "0000000000000000000000000000000000000000"
  },
  "credentials": {
    "clients": [{ "instanceId": "28800bc6-eb1d-4fa7-817d-546587e2eceb", "reference": "desktop-a" }],
    "receivers": [],
    "senders": []
  }
}
```

Use existing library and registered desktop IDs. Provision Linux Secret Service entries with attributes `application=beets-man` and `reference=<reference>`. On Windows, provision a Generic Credential named `BeetsMan/<reference>` with a UTF-16 password. The host reads client credentials at startup and checks each request against the instance's current registration. Restart the host after changing a client credential.

Each Android export adds an `androidExports` entry with `deviceId`, `folderId`, and a `sender` object containing the local Syncthing `endpoint`, `deviceId`, and dedicated `exportRoot`. Add a `receivers` entry keyed by `deviceId` and a `senders` entry keyed by `syncthingDeviceId`, each with its own `reference`. The host looks up those credentials on demand.

To pair an active Android registration before it has an export binding, set `receiverEndpoint` on its `androidExports` entry. `receiverRoot` can specify a dedicated receiver path, otherwise the host uses the approved profile's suggested root. Set `caseSensitivePaths` if the new receiver requires case-sensitive path comparisons. Existing bindings supply their registered endpoint if the host option is absent.

The optional `pcMirrors` array has `peerId`, `folderId`, `receiverEndpoint`, `receiverRoot`, `senderEndpoint`, and `senderDeviceId`. Use an active desktop registration with a matching native Syncthing ID. Add the peer's `receivers` reference and the sender's `senders` reference. The full library's configured `musicRoot` is the expected send-only folder path. The desktop accepts the matching receive-only folder at its configured root.

Add `host.beets` with the absolute `executablePath` and `catalogPath` to enable the import worker. An optional `albumPathTemplate` overrides the native beets relative naming format. Set `createCatalogIfMissing` when provisioning a new beets library. To enable MusicBrainz matching, add `host.beets.matching` with an absolute `ffmpegExecutablePath`. Its optional `endpoint` selects the MusicBrainz HTTPS origin or a loopback HTTP fixture. The default is `https://musicbrainz.org`. MusicBrainz receives the album and album-artist search terms and the release IDs. Staged audio stays on the host.

Set `host.beets.configurationPath` to the approved native YAML location. It defaults to `beets-library/config.yaml` under the host publication work root. Library Setup projects the provisioned host values and lets an active Operator explicitly initialize them. The host preserves existing files, stages native artifacts privately, and installs both files before returning the accepted revision. Matching uses its own private configuration and does not enable a plugin in the base YAML.

Set `host.beets.allowedPluginIds` to the installed native modules approved by the host owner. The desktop can select from those IDs, and the host confirms that beets loads them before saving. Committed naming, import behavior, and plugin edits apply to subsequent native commands through the generated per-revision YAML. Library relocation is handled in host launch configuration so the beets catalog and media shares remain aligned.

## State ownership and entry points

- **Bootstrap and preferences.** Resolve and validate local appsettings, the database path, the music root, and logging before opening normal services. Start a recovery shell with the available diagnostics if configuration is invalid. Settings handlers resolve local override, last valid shared default, then built-in value. Restart-bound values stay in bootstrap configuration. Registry-backed ordinary preference edits update the relevant projection.
- **Registered desktop composition.** `DesktopHostBinding` takes the existing HTTPS endpoint, the caller's credential provider and HTTP client, and optional import selection and private file storage. `DesktopStartup` builds one dispatcher over the validated store. Playlist drafts, queue auto-save, and the registered host's tag, import, organization and removal handlers use the same `LibraryBatchHandlers` instance and desktop scope. Cached reads, drafts, and the local batch remain available before a host transport is attached. Replication and publication use the supplied registration.
- **Desktop enrollment and revocation.** The host maps each provisioned credential to a library and desktop identity. The optional `canManageRegistrations` on that credential reference grants the Operator role. `OperatingSystemDesktopHostCredentials` resolves the selected reference from the local Windows Credential Manager or Linux Secret Service and supplies the normal registered-host credentials. `HttpDesktopRegistrationHost` sends the commands under the configured endpoint. No credential value enters the roster, operation receipt, or CQRS request.
- **Dispatch and presentation.** The bound MVVM Toolkit command submits one typed request with a correlation ID and cancellation. The handler returns a scoped result. The presentation projection accepts only the current page request, dialog owner or playback session, and posts every application-driven update through one Avalonia dispatcher adapter. Serialize writers by the state they own. Keep navigation responsive while host operations run.
- **Catalog, queue, and playlist drafts.** Catalog queries return stable artist, album, track, and playlist IDs. The playlist workspace owns drafts and their ordered IDs. The playback coordinator owns the active queue. A new playlist draft can start from an immutable queue snapshot. Playlist save carries the stable operation ID and expected revision when editing a saved playlist. A validation failure preserves the draft.
- **Local batch control.** `LibraryBatchHandlers` scopes typed staged edits to the registered desktop and library. The desktop LiteDB store keeps the toggle, ordered changes, and receipts on its existing transaction lane. Tags, named playlist saves, and queue auto-save share the mode gate. The tag editor overlays pending changes on its local catalog baseline. The playlist editor keeps the draft's published backing until it receives a host receipt. Queue auto-save commits its checkpoint with the staged save, then reads the original operation's published version after commit. `QueuePlaylistPublication` checks that version within the mode gate before staging another edit. Background playlist replay waits for batch mode to turn off. Staging invalidates the previous review. Commit seals the reviewed revision and operation before crossing the publisher port. Revert discards the staged records and retains replay guards.
- **Approved batch admission.** `HttpApprovedLibraryBatchPublisher` submits the frozen review to `HostApprovedLibraryBatches`. The host stores ordered effects, native track identities, and operation reservations in `LiteDbApprovedLibraryBatches`. Playlist-only effects share one revision and return the final playlist versions. The desktop binds named drafts when it records the returned batch receipt.
- **Approved native batch execution.** `NativeBatchWorker` shares the serialized beets lane and existing organization, tag, catalog-removal and approved audio deletion adapters. `LiteDbNativeBatchWork` rechecks the scoped targets, reserves affected playlists, and persists the execution cursor with file fingerprints. Recovered moves determine the later native catalog path. The reserved audio plan determines the exact file deletion path, with fingerprints carried forward only from verified edits to that file. The host resumes from the cursor and commits the verified catalog, playlist, delivery and approval records together. A batch with any unsupported entry stays accepted in full.
- **Approved batch import transfer.** `HostApprovedBatchImports` resolves the file from the frozen host journal before reading the request body. It uses `FileImportStage` in a separate batch namespace. The host records the verified ordinal only after the copy succeeds, and the desktop resumes by comparing those receipts with its frozen review.
- **Approved batch guided review.** `ApprovedBatchImportReviewWorker` verifies a complete entry in its private batch namespace and uses the existing guided matcher. `LiteDbApprovedBatchImportReviews` stores the public comparison, private match identities, revision and decision. `LibraryBatchHandlers` exposes CQRS review and choice requests tied to the local seal. `HttpApprovedLibraryBatchPublisher` checks the batch identity, entry, returned file names and choice receipt before handing results back to the desktop.
- **Approved batch import execution.** `NativeBatchWorker` waits for every import choice, verifies the private inputs and prepares matched files before native work. Each import uses its choice operation as the native beets marker. The journal persists the attempt before invocation and checkpoints the verified album together with the next entry position. After restart the worker reads the marked album before it considers another write. `LiteDbNativeBatchWork` projects verified import albums with the rest of the batch using the shared catalog projection. Skip has no native effects, and an all-skip approval returns the existing feed head.
- **Approved batch withdrawal.** `LibraryBatchHandlers` discards an unsubmitted batch locally. For a sealed approval, it checks the authenticated `IApprovedLibraryBatchWithdrawal` receipt before clearing the reviewed entries and releasing desktop copies. `LiteDbApprovedBatchWithdrawal` serializes against admission and the native start checkpoint. A withdrawal received before admission reserves the approval and batch identities without storing changes. Starting or publishing the batch closes its withdrawal window.
- **Desktop maintenance confirmation.** `LibraryMaintenanceHandlers` registers organization and removal on the same typed dispatcher as other library commands. `HttpLibraryMaintenanceHost` uses the registered HTTPS endpoint for previews and confirmations. The ViewModel retains the displayed plan and operation ID across an uncertain response. The local mode gate stages approved maintenance with its exact selection, paths, and removal mode and keeps the host confirmation private until the batch is approved for publication.
- **Local maintenance projection.** `LiteDbCatalogReader` applies the owning desktop's staged maintenance while holding the same LiteDB lane used to read the catalog. `LocalMaintenanceCatalog` indexes removals and proposed paths by track identity. The playback resolver still reads the committed media path for a visible track, and the published playlist reader returns the committed playlist for save and revision checks.
- **Library removal execution.** `CatalogRemovalWorker` uses the shared beets execution lane to check the pinned items and persist the start checkpoint. Catalog-only removal retains the files. `AudioRemoval` verifies the separately approved bytes, removes each native item, and delegates scoped file deletion to `BeetsAudioRemoval`. `LiteDbHostPlaylistStore` waits for verification before committing track deletions, tombstones, notifications, and job status together.
- **Organization execution.** `OrganizationWorker` uses the same native lane and scopes each copy to the frozen maintenance plan. The adapter verifies the original and copied bytes before repointing the same beets record. `LiteDbOrganizationWork` stores the ordered copy manifest and commits the changed paths, notification records, and job status together.
- **Incremental catalog replication.** `CatalogReplicaHandlers` pulls a fixed window through `HttpCatalogReplicaHost`, commits each page through `ICatalogReplicaStore`, then acknowledges the durable cursor. The versioned feed contract validates scoped contiguous revisions. Host LiteDB reads the committed change journal and independently acknowledges each recipient. Desktop LiteDB stores the catalog changes and checkpoint atomically.
- **Automatic recipient refresh.** `DesktopReplicaRefresh` starts with a registered workspace and submits `RefreshReplication` every two seconds after a successful response. It backs off after failure and returns to the normal interval on success. Automatic refresh and manual recovery share the replica handler's serialization. A lost acknowledgement retries without reapplying the completed page. Each desktop owns its refresh loop, so one offline peer cannot delay delivery to another. Shutdown joins the loop before disposing LiteDB.
- **Playlist reconnect.** After a successful incremental refresh, `PlaylistWorkspaceHandlers` replays named saves and `PlaybackSessionHandlers` replays pending queue auto-saves from the registered desktop's outbox. Both reuse the direct publication path and pause while batch mode is enabled. Queue recovery releases the playback command lane during publication and reacquires it to apply the stored result to the current session. Named saves reuse the original payload and retain the local draft and observed host revision on conflict.
- **Shared library records.** `HttpLibraryRecordHost` verifies the scoped write receipt from `HostLibraryRecords`. `LiteDbLibraryRecords` stores favorites, distinct plays, and eligible preference defaults with their operation receipt and feed deliveries in one transaction. Favorite and default deletions retain their revision after snapshot recovery, so later edits can send an exact expected revision. The versioned allowlist currently contains the documented automatic fade duration.
- **Desktop listening outbox.** `LibraryRecordHandlers` implements the favorite and play CQRS routes and runs during `CatalogReplicaHandlers` recovery. `LiteDbLibraryRecordOutbox` journals the original intent and pins an ordered favorite's expected revision before a send. It commits a confirmed result and the accepted outbox state together. `LiteDbLibraryRecordConflicts` projects saved drafts and applies reviewed Keep Host or Reapply Local decisions without replacing pending operations during snapshot recovery.
- **Listening capture at playback.** `PlaybackSessionHandlers` tracks the confirmed occurrence for each deck. When configured with a registered listener scope, it stages the play via `IPlaybackHistoryCheckpointStore`. `LiteDbPlaybackCheckpoints` commits the play and queue state together, recognizes an exact lost receipt, and restores the primary occurrence for that queue entry. The outbox handles later publication.
- **Playlist playback across restart.** After validating configuration, `DesktopStartup` opens the local store and uses its persistent `StoreId` as the playback session ID. It calls `InitializePlayback` once for the active workspace. `PlaybackPreferenceHandlers` reads the local `playback.resumeAfterRestart` toggle, which defaults to off. `PlaybackSessionHandlers` can resume a previously playing saved playlist from its exact checkpointed entry and position. SoundFlow opens the system playback device when a deck first needs it. Before stopping the workspace, the caller stops submitting work and calls `StopAsync`. That invokes `SavePlaybackForRestart` and keeps the workspace open if the checkpoint fails, so the caller can retry. Final disposal attempts a checkpoint and closes the audio device and store.
- **Native mixer.** `PlaybackSessionHandlers` validates and serializes mixer and EQ requests with transport. `SoundFlowDecks` keeps each deck's gain separate from its crossfader multiplier. The master mixer controls the combined level. `SoundFlowMasterEqualizer` prepares a replacement filter bank on the control side and publishes it to the render path together. Bypass leaves the configured bands available for reactivation. `SoundFlowPlaybackOutput` retains accepted controls while the system audio device is closed and applies them when a deck opens it. [SoundFlow mixer source](https://github.com/LSXPrime/SoundFlow/blob/0a1f2c98ba13fa40fffe720fafe60d8f52ae81fd/Src/Components/Mixer.cs)
- **Native visualization source.** `SoundFlowVisualizationCapture` samples the master mixer after EQ and volume. Its render callback writes to one fixed sample window and skips capture under contention. `IPlaybackVisualizationSource` provides bounded waveform and frequency values to readers on demand, with duplicate and expired frames filtered at the source. [SoundFlow processing order](https://raw.githubusercontent.com/LSXPrime/SoundFlow/v1.4.2/Src/Abstracts/SoundComponent.cs)
- **Automatic playback.** `DesktopPlaybackPump` drives a mixer-capable workspace with non-overlapping `AdvancePlayback` commands. `PlaybackSessionHandlers` measures the blend from decoded audio position, confirms the incoming deck before changing levels, and checkpoints its exact queue entry on promotion. The same clock drives the existing playback ViewModel. Orderly shutdown joins the loop before recording the final position. A failed checkpoint leaves the workspace and loop available for retry.
- **Catalog snapshot recovery.** `LiteDbCatalogSnapshots` captures one ordered catalog snapshot per registered recipient and reopens the same capture when its request is retried. `LiteDbCatalogSnapshotReplica` retains private pages across restart and checks their scope, position, and capture identity before replacing the synchronized entities and checkpoint in one transaction.
- **Playback, CLI and extensions.** Transport commands target the active playback session. Presentation mode references that session by identity. The native audio and configured CLI adapters implement capability-aware playback contracts. Switching backends preserves the queue and selected track and waits for Play. A separately trusted worker can contribute a visualization or submit a registered action through CQRS. The audio callback exchanges bounded state and samples, so worker activity and logging do not block it.
- **Local CLI profiles.** `CliProfileHandlers` registers load, validate, and save requests on the desktop dispatcher. `YamlCliProfileStore` stores an atomic, revisioned YAML file per profile in `playback-profiles` beside the configured desktop settings. A one-shot action declares separate argument tokens. A session action declares a request kind. Both declare how to read reply fields and map worker states. Validation and saving do not start a process.
- **CLI playback process.** `CliPlaybackOutput` resolves the track to a local catalog path and maps a validated profile to the playback transport port. `CliPlaybackProcess` substitutes whole argument tokens for one-shot commands or sends a correlated request to one session process. It bounds reply length and latency, discards stderr, and reaps the owned process on timeout or protocol failure. A new session after failure requires explicit Play.
- **Playback strategy handoff.** The playback coordinator binds a proposal to the selected engine, saved profile revision, queue revision and active entry. Clock updates leave that proposal valid. Confirming stops the prior decks before replacing the engine. The session keeps the exact queue and selected occurrence and waits for Play. While CLI is selected, the native audio clock does not poll the worker. Desktop shutdown saves restart state before stopping external playback and disposing the worker.
- **Local plugin registry.** `LocalPluginPackages` captures a file selection, validates its ZIP and versioned manifest, and keeps a verified digest-addressed copy outside the library feed. `PluginRegistryHandlers` commits an admitted version with trust and enablement initially off. Each update requires its own local trust. Enabling a trusted version of an installed plugin disables the earlier version in the same transaction.
- **Plugin worker handshake.** `PluginWorkerFactory` requires a local, compatible and enabled registration. It rechecks the archive digest and manifest, extracts into a private working copy, and starts the declared .NET assembly without shell invocation. The version 1 protocol validates the greeting identity and each offered contribution against the installed manifest. A failed negotiation stops the process and releases the working copy. `BoundedTextProcess` provides the same bounded UTF-8 framing and child cleanup for plugins and CLI playback.
- **Plugin supervision.** `PluginWorkerSupervisor` observes committed registry changes and negotiates children without holding the desktop, playback, or navigation lanes. It publishes a new projection when negotiation succeeds or a worker exits, and immediately excludes retired versions from that projection. Replacing a worker waits for the prior process to close. The desktop monitor publishes status to the Extensions ViewModel and joins worker cleanup before closing the local store. A recovery session suppresses process activation while retaining configured local trust and enablement.
- **Plugin action dispatch.** `InvokePluginAction` captures the active session, exact installed worker, contribution ID, and bounded plain arguments. The worker exchange uses a fresh correlation ID and preserves the application operation ID. The supervisor rechecks the same live worker before admitting a host effect. A reply can request `playback.pause` only from an action whose admitted manifest grants it. The host maps the grant to the existing typed `Transport` command and projects its confirmed result. Failed worker exchanges close the process without occupying the playback lane.
- **Declarative plugin panels.** `GetPluginPanel` projects the installed field definitions and the current track for an exact worker activation. `SubmitPluginPanel` validates user text, binds the host-owned track, and resolves the manifest-linked action through the same worker action route. A changed track or replaced activation invalidates the captured submission.
- **Visualization selection and routing.** `VisualizationSession` keeps selection and preview revisions independent of transport. It reads the current backend capability and a fresh mixed window before projecting Waveform, Spectrum, or bounded levels from the exact selected worker activation. The desktop polls for the latest window and expires projections while an exchange is in flight. Changing audio context or selection drops prior frames. A failed worker detaches its visualization while playback and built-in choices remain available.
- **Shortcut settings.** `ShortcutHandlers` normalizes gestures, keeps defaults in `ShortcutCatalog`, and commits contextual overrides at their LiteDB revision. Resolution checks the active dialog before the active views. The separate platform port applies only opt-in playback key sets and reports the accepted state on a runtime revision. A denied request leaves the local set usable, and the desktop releases platform registrations when it closes.
- **Preference registry and reset.** Playback and Notifications use the same typed registry and precedence rules. The host replicates the eligible fade duration and sync-completion flag. A reset proposal captures only the category's explicit overrides and the values they would inherit. Its commit checks the local revision and cached shared revision inside the LiteDB transaction before clearing those overrides together.
- **Windows system playback keys.** `Win32ShortcutPlatform` owns user32 registration and activation notifications on one background message thread. A denied replacement releases newly acquired keys and retains the prior set. `DesktopSystemShortcutDispatch` checks the accepted registration revision before dispatching a typed transport command. The Play or pause action resolves the toggle inside the playback command lane. [Windows RegisterHotKey](https://learn.microsoft.com/en-us/windows/desktop/api/winuser/nf-winuser-registerhotkey) · [WM_HOTKEY](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-hotkey)
- **Linux system playback keys.** `XdgShortcutPlatform` keeps each candidate portal registration and its signal subscription on its own D-Bus connection. Before opening a shortcut session, an unsandboxed desktop registers `io.github.sharpninja.BeetsMan`. Install [its desktop entry](../../src/BeetsMan.Desktop/Packaging/io.github.sharpninja.BeetsMan.desktop) in an XDG `applications` directory with the desktop executable. If host registration is unavailable or the sandbox supplies the identity, the portal decides whether to open the session. Accepted trigger descriptions project into the same shortcut state used on Windows. A failed replacement closes the candidate session, while an external remap or closure refreshes the open editor and advances the system revision. [XDG Registry](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.host.portal.Registry.html) · [XDG GlobalShortcuts](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.GlobalShortcuts.html)
- **Guided import intake.** `HostImportIntake` accepts a manifest and streamed copies from the active registered desktop. It keeps verified bytes under the private staging root and accepts a single job per upload in LiteDB. The desktop uses `IImportSourcePicker` to obtain local selections and `HttpImportIntakeHost` to submit ordered checksums and copies over registered-host TLS. `HostLibraryViewModel` retries the same operation after a lost start response, recovering the job without recopying accepted files. The native picker is pending.
- **Batched import copies.** `FileLibraryBatchImportStage` holds verified copies outside the synchronized music tree. `LibraryBatchHandlers` persists file ownership before copying, retains the bytes while their review remains active, and releases unadmitted or retired copies using the durable claim. The hosted import mutations share the desktop mode gate. `HostLibraryViewModel` accepts the local stage receipt when batch mode is enabled, including while disconnected.
- **Guided import execution.** `HostImportReview` records one album review and validates the originating desktop's choice against the offered item and job revision. Skip ends the job. Keep tags uses the verified upload. Use match prepares new tagged copies in private and verifies their release tags and encoded audio. `GuidedImportWorker` records the native attempt and verifies its effects before `ImportCatalogPublication` commits an album, the job result, and peer deliveries at one revision. A retry reconciles any existing live attempt. Readback retains the disc and year observed in beets.
- **Track tag editing.** `TagEditViewModel` loads the current track tags and reuses the same operation ID when retrying a matching save. `HostTrackTags` validates the patch and the LiteDB adapter records the revision-pinned job and receipt in one transaction. `TrackTagWorker` checks the current beets item and embedded tag state, records the attempted write, and verifies both stores after applying it. The worker and guided imports run sequentially. A restart can publish the already-written tags from readback while preserving the original job ID. Edits to one track's album or album artist are stored with that track's tags and preserve its existing album membership.
- **Maintenance previews and admission.** `HostLibraryMaintenance` checks the registered desktop, ordered selection, and current catalog revision. Its beets adapter previews organization paths and fingerprints the audio candidates. The LiteDB adapter stores the reviewed kind, paths, target snapshots and audio fingerprints. Confirmation rechecks the pinned revision and mode and records one accepted job with an operation receipt. Only the preview that includes audio can authorize audio deletion.
- **Device export.** The registered desktop dispatcher connects Sync list edits, layout reads, review, publication, transfer status, and PC mirror commands to the authenticated host adapter. The Sync drop sends the saved playlist ID, destination, and selected profile revision. `HostDevicePlaylistStager` resolves the device inventory, generates the original ordered playlist, and commits the plan, missing-audio entries and replayable receipt. Generated bytes stay outside the active share until publication. [Media layout and Android navigation](../stage-0/contracts.md#media-layout-and-android-navigation)
- **PC mirror control.** `HostPcMirrors` serves the authenticated media directory and routes the existing desktop CQRS commands through `SyncthingPcMirrorControl`. The adapter verifies the native IDs, full-library sender root and exact receive-only folder. It patches only the receiver's pause flag and rescans only that folder. LiteDB keeps the most recent verified file count while the mirror is paused and retains operation receipts across host restart.
- **Media share offer.** `SyncthingMediaShareOffer` verifies the registered native sender and receiver, then offers the configured full-library mirror or dedicated Android export on the sender. A PC mirror can add one recipient while preserving the earlier recipients and their settings. Android offers restrict the sender folder to the host and selected device. The receiving device accepts the folder through Syncthing. [Syncthing configuration API](https://docs.syncthing.net/rest/config.html)
- **Pairing approval.** `MediaSyncViewModel.ShareFilesCommand` dispatches `PairMediaPeer` through the desktop's authenticated host adapter. `HostPcMirrors` serializes it with the mirror operations. The host claims the proposal at its expected media directory revision, then calls `SyncthingMediaShareOffer`. Its LiteDB repository commits the approved binding and original response together. The paired Android layout becomes available to the existing layout and export-plan queries.
- **Android arrivals.** `SyncthingAndroidArrivalWorker` verifies the configured sender and advances through the native connection stream. Startup, native restart and a cursor gap establish a silent baseline. With a presentation scheduler and registered host, `DesktopStartup` activates the shell and Sync ViewModels, then starts one authenticated `AndroidArrivalMonitor`. The monitor dispatches `ApplyAndroidPeerArrival` and loads the selected peer through `GetMediaSyncState`. A desktop reconnect also begins with a silent baseline. Orderly shutdown cancels and joins the poll before disposing the ViewModels on their scheduler.
- **Receiver inventory.** `SyncthingReceiverInventory` verifies the receiver identity and reads exact paths from its local index. For paired exports, inventory and transfer checks both require the approved receive-only folder, exact root, and approved sender and receiver before and after the index read. The media status query reports an accepted and unpaused folder as `Ready`. Unknown receiver state, ambiguous absence and occupied non-file paths prevent using those index results. [Syncthing configuration API](https://docs.syncthing.net/rest/config.html) · [Syncthing file index](https://docs.syncthing.net/rest/db-file-get.html)
- **Player layouts.** `AndroidLayoutProfiles` validates the versioned YAML and supported playlist format. The bundled Musicolet v2 and Poweramp v3 layouts use album-based paths and relative M3U8. Add absolute paths to custom layout YAML under `host.androidLayoutFiles` and restart the host to load them. Use unique profile IDs and ordinary local files outside the synchronized media trees. Custom profiles can choose a registered format such as PLS. `RegisteredDevicePlaylistResolver` uses the selected revision with the library catalog and registered receiver before staging. [Poweramp playlist formats](https://powerampapp.com/)
- **Device export reads.** `HostDeviceExportReader` reloads layout choices and a scoped plan over authenticated HTTPS. The desktop includes the selected profile version and optional plan ID. The host serves ordered persisted entries and checks both the caller and the current Android share before returning them.
- **Host composition.** `LibraryHostStartup` validates the configured music, private storage and Android export paths and registers all implemented playlist and device-export routes. The snapshot reader, file publisher and Syncthing sender share one configured library, device and folder binding. Caller authentication and sender and receiver credentials enter through separate services.
- **Export publication preview.** `FileDeviceExportSnapshotReader` inspects the configured share and hashes relevant file contents. `DeviceExportPublicationPlanner` compares the staged files with the prior ownership manifest and observed share contents. Ordinary publication preserves owned files outside the staged list. Layout reconciliation recognizes reviewed moves by stable source and content and requires explicit approval for standalone removals. A changed share registration, plan, manifest, or action set invalidates an earlier approval.
- **Export publication journal.** `IDeviceExportPublicationJournal` binds one active publication to the registered share and the originating operation. The host can reopen the same file actions after interruption. Verified step progress leaves prior ownership intact. After the final step, a single LiteDB transaction publishes the next ownership manifest and stores the original receipt.
- **File application.** `HostDeviceExportPublisher` rechecks the registered share and records each verified step. `FileDeviceExportStepWriter` retains the previous owned bytes in private work and checks source and destination digests before changing the share. Publication uses same-directory temporary files that Syncthing excludes from synchronization. Retrying an interrupted step checks its private record and resulting bytes before proceeding. [Syncthing temporary files](https://docs.syncthing.net/users/syncing#temporary-files)
